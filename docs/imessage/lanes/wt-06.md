## Authentication and data flow

The r2 topology is portal → web UI → core, with separate processes. `plugins/portal/src/index.ts` checks its session and same-origin mutation requirements. Its proxy strips client identity headers and mints a short-lived `x-portal-identity`. Web UI `authenticate()` checks that identity and its principal allowlist; `handler()` retains the token in its existing `AsyncLocalStorage` scope. Existing resource routes and `coreFetch` bind the current principal and carry source authentication and portal identity to core. No token is returned to the browser by this host.

Integration inserts `createPhotonHostRoute(options)` into the existing authenticated `apiRoutes` array. Its only route is `GET /api/photon/host`. It must remain inside `routeRequest`'s existing `/api/` identity gate and `handler`'s request scope. The route does not authenticate a forwarded URL or accept a viewer in its query. `resolveAuthority(req, request, viewerId)` must resolve current installation, project, line, conversation, session and exact resource access using canonical QM and transport bindings; it returns `{ viewerId, context }` only on current authorization, and `null` on denial. Missing binding implementations must return denial, never echo the URL as proof.

After comparing the checked context with the complete requested scope, the route calls the supplied `PhotonContributionProvider.forConversation(conversation, viewerId)` for this viewer. It checks the returned conversation and selects exactly one registered `(view, resourceId)` mount. The JSON response allowlists the validated context, current viewer, contribution ID and selected mount metadata. Other mounts, actions, implementation objects, credentials and private fields are omitted. Responses use `Cache-Control: no-store`. There is no host mutation dispatcher: existing views continue to use existing QM APIs and their normal authorization/revision controls for every mutation. The metadata response is never a mutation capability.

Unknown/duplicate query fields are rejected. r2's view union is authoritative; `search` is not assumed present. `audience: conversation` is presentation metadata and cannot grant conversation members authority. `webPath` is a canonical same-origin path; only the existing `scope` query is accepted, with no fragment, bearer token, alternate origin or normalized traversal. Adapters generate paths through existing deep-link helpers. Public static entry/preview metadata must remain generic; sensitive titles/content are obtained only after authentication.

## Contribution lifecycle and presentation

Each navigation, reconnect, visible-tab refresh or bfcache restore aborts the previous request and removes its rendered subtree before requesting fresh context. Sequence checks prevent late context responses from mounting. A stale asynchronous mount receives an aborted signal, retains only a detached root, and has its returned cleanup called. Successful mounts provide the heading and normal QM handoff link. Identity changes, denied context and unregistered views leave an unavailable state without retained private content. Sign-out, offline and pagehide suspend the view. Remounting the same root disposes the earlier host; disposal is idempotent and removes navigation, window, document and button listeners.

Navigation is constrained to the initial provider/installation/project/line/conversation. Session and resource changes still require a new server check. Browser Back/Forward reuse parsed URLs and reauthorize; the host Back button becomes available only for its own in-memory navigation history. Marked `a[data-photon-navigation]` links preserve modified clicks/new-tab behavior. This history is disposable presentation state, not a durable business store.

`compact`/`expanded` are local layout choices, set through `setLayout`. They do not claim Messages presentation-mode detection. The header wraps, controls are at least 44px, focus remains visible, the content has an independent scroll area, and CSS uses safe-area insets, logical spacing, dark and forced-color modes. No global CSP, frame policy, source identity configuration or untrusted-content sandbox is changed. `Open in QM` is an ordinary authenticated handoff.
