## Boundary

The channel accepts a frozen `NormalizedPhotonInput` and one exact `QmChannelOperationRequest`. The source-auth gate first verifies the surface process, request method, complete path including its nonce, and body. Core authorization then independently resolves current installation state, canonical human identity, conversation-to-session binding, current session visibility, capability scope revision, run ownership, and action binding where applicable. The checked proof supplied by a caller is discarded and recomputed immediately before execution.

Only `turn.start`, `turn.steer`, `run.signal`, and `approval.resolve` are executable in this lane. Other frozen operation names fail closed with `operation_authority_unavailable` until their existing QM owners are deliberately linked by their owning work. No generic operation executor or duplicate business owner was added.

## Factories and wire shapes

- `createPhotonAuthorization(deps)` constructs the fail-closed current-state authority from narrow installation, identity, conversation, action, run, and existing App ports.
- `createPhotonCoreClient(deps)` maps authorized operations and surface-system reads to existing App and store methods.
- `createPhotonRoutes({ core })` returns source-authenticated private routes without registering them globally.
- `createPhotonQmClient(deps, source)` binds one normalized source event and returns the plugin-side signed client. Its `check` and `execute` methods satisfy the frozen `QmChannelAuthorityPort`; its read/control methods use the same source envelope where human authority is required.

The HTTP human-operation body is exactly `{ source: NormalizedPhotonInput, operation }`. System delivery and context routes carry no human identity claim and remain restricted to source authentication plus a fixed `photon` surface check in core.

## Idempotency and retries

Natural input uses an internal structured redelivery key derived from `provider`, `installationId`, nullable `lineId`, and `eventId`. The operation must carry that exact key and the exact normalized source request. It is passed only to the existing internal `App.turn` path, so ordinary input can still steer or halt an active run. The public turn route still removes caller-supplied `redeliveryKey`.

Explicit signals and approval replay use a separate structured key containing `provider`, `installationId`, nullable `lineId`, `conversationId`, `eventId`, and the frozen logical `idempotencyKey`. This scopes the existing durable deduplication paths without replacing them.

Each HTTP attempt receives a fresh `_sourceAuthNonce` before signing. Read-safe requests retry transient server and transport failures. `turn.start`, `turn.steer`, and `run.signal` may retry because their core effects carry stable duplicate protection. Approval resolution, queued withdrawal, delivery acknowledgement, and context fulfillment are never blindly retried. A transport failure, invalid success response, or server error on those mutations is reported as `unknown-outcome`; callers must reconcile before another attempt.

## Registration and evidence boundary

Integration must construct the authorization and core factories with the assembled durable Photon installation, identity, conversation, and action-binding ports plus QM run and delivery stores. It must then add `createPhotonRoutes({ core })` to the integration-owned API route composition. Every Photon `POST` path must also be classified as system-to-system in the integration-owned `src/api/user-scoped-routes.ts`; otherwise production portal-identity enforcement intentionally rejects an unclassified source-auth write. The existing classification regression must be expanded over the registered Photon routes. Photon runtime composition must construct `createPhotonQmClient` with the same core URL and source-auth secret and inject its checked `QmChannelAuthorityPort` into the intake owner. Those are exact registration requirements; this lane does not edit `src/api/routes/index.ts`, `src/api/user-scoped-routes.ts`, server wiring, package registration, shared contracts, or durable Photon implementations.

Inbound attachments fail closed with `photon_attachments_not_linked` until their owned durable staging path is assembled. Unsupported frozen QM operation names remain closed rather than acquiring guessed policy. This lane provides local typecheck and focused-test evidence only. It does not establish integration assembly, route activation, a live Spectrum connection, provider acceptance, delivery or read evidence, or physical-device behavior. The fully linked round trip remains unclaimed until the early Wave B gate.
