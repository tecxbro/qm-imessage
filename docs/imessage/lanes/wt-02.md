## Process and credential boundary

`PhotonCliProcess` accepts only the typed operations in the table. It invokes the executable with `shell: false`, ignores stdin, bounds combined stdout and stderr, applies per-command timeouts, terminates on cancellation, and reduces nonzero output to a safe error code. Successful stdout is private return data for the setup modules and is never logged by the boundary.

Each installation receives a SHA-256-named directory beneath the injected absolute config root. The subprocess receives that directory as both `PHOTON_CONFIG_DIR` and its isolated home. It receives a small environment allowlist; ambient Photon tokens, project IDs, project secrets, Spectrum secrets, and agent environment variables do not cross the boundary.

The config root, installation parent, installation directory, and credential subdirectories are mode `0700`. Files below them are mode `0600`. Symlinks and non-file/non-directory entries below the config root fail closed.

## Login and installation lifecycle

`PhotonDeviceAuthorizationParser` accumulates the real stdout/stderr stream, removes ANSI control sequences after chunk assembly, and publishes exactly one authorization display only after complete newline-terminated `Visit` and `Code` fields are present. It accepts only credential-free HTTPS URLs on `https://app.photon.codes`. Arbitrary chunk boundaries, including boundaries inside ANSI sequences and labels, are covered.

`PhotonCliInstallationService` is the shared orchestration service for the dashboard and QM CLI. Every stored transition increments `InstallationRecord.version` through `InstallationStorePort.compareAndSet`. Concurrent `start` or `resume` calls in one service instance share the active visible result and completion. Separate service instances serialize through the durable `provisioning` and `awaiting-authorization` states; a losing compare-and-set observes the winner without launching another login or overwriting its state.

Project selection is always by exact provider ID. Duplicate display names have no special meaning. `create-project` is a distinct explicit setup action. After creation, the returned project ID is durably stored before the existing project secret or assignment is read, so resume never repeats project creation once an ID is known. `projects secret` reads an existing credential; it does not rotate one.

Assignments are explicit. `shared-recipient` matches one actual provider user by E.164 address and uses that returned user ID as the stable shared-pool assignment scope; the pinned CLI's user contract does not expose a dedicated-line ID. If the provider also returns an assigned sender number, only its mask reaches public status. `select-line` matches one actual provider line by ID. Absence or ambiguity fails without fabricating an ID.

| Durable private state     | Private material allowed                                                         | Dashboard projection                                                 |
| ------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `not-started`             | None                                                                             | Installation ID only                                                 |
| `provisioning`            | Credential path and, after its checkpoint, existing project secret               | Installation ID only                                                 |
| `awaiting-authorization`  | Credential path and trusted management origin                                    | User code, trusted verification URL, bounded expiry, installation ID |
| `connected`               | Credential path and existing project secret through the injected encrypted store | Project ID, actual line IDs, masked addresses, installation ID       |
| `needs-owner-rebind`      | Previously stored private fields may remain durable                              | Installation ID only                                                 |
| `needs-credential-repair` | Management credential state remains separate                                     | Installation ID only                                                 |
| `failed`                  | Previously stored private fields may remain durable                              | Installation ID and safe code only                                   |

The service always uses `projectInstallationForDashboard` for stored-state projection. No access token, raw CLI output, credential path, device code, full address, or project secret enters a public result or log.

Management login expiry and runtime credential health are independent. `managementLoginStatus()` can report `reauthorization-required` while a complete connected runtime record remains connected. A connected record lacking its stored runtime secret projects `needs-credential-repair`; no automatic repair or rotation command runs.

## Restart, cancellation, and cleanup

An `awaiting-authorization` record from a prior process is not reattached because the exited CLI subprocess is gone. `resume()` records `PHOTON_REAUTHORIZATION_REQUIRED`. An explicit later `start(action)` may begin a new login.

A `provisioning` record with a durable project ID validates the installed command and management login, selects that exact stored project, and resumes with the explicit assignment. It never creates another project. If the CLI credential has expired, resume records `PHOTON_REAUTHORIZATION_REQUIRED`. A provisioning record without a project ID records `PHOTON_PROJECT_SELECTION_REQUIRED`; it does not guess a project.

Cancellation aborts and awaits the child and records `PHOTON_SETUP_CANCELLED`. Service close aborts and awaits the child while preserving the latest durable checkpoint for restart. Denial, expiry, cancellation, timeout, malformed output, missing assignment, ambiguity, owner revision changes, and CAS conflicts cannot project `connected`.

The QM CLI must call the same service, print only the returned display status, and use `waitForCompletion()` after showing the device authorization. It must not print successful subprocess stdout, inspect credential files, or place their contents in an agent environment.

After durable storage startup, the runtime supervisor must call `resume()` only with an explicit assignment for a durable provisioning record. A connected public status is necessary but does not by itself prove provider credential acceptance or Spectrum activation.
