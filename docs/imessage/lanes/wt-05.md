## Before and after helper semantics

| Boundary                     | Before                                                                                                                                                            | After                                                                                                                                                                                                                                                                                                                 |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Named reach                  | A person always became a generic `principal` destination, a channel always became `slack`, and a participant set always used the Slack group directory/open flow. | An omitted surface follows those paths byte-for-byte. An explicit `photon` surface asks an injected resolver for a registered, structured DM or group conversation. Photon cannot claim a Slack channel or generic destination. Resolver absence and invalid results fail closed. Ambiguous results remain ambiguous. |
| Group registration           | A missing Slack group could be opened and then additively registered.                                                                                             | Slack behavior is unchanged. A resolved Photon group is additively registered with its complete canonical participant set; no member or unrelated Slack group is replaced.                                                                                                                                            |
| Current-conversation actions | Reaction, deletion, and edit references were bare message strings.                                                                                                | Slack retains the bare fields. A validated Photon destination additionally carries the full provider, installation, line, conversation, message, and optional part reference.                                                                                                                                         |
| Surface context              | The current destination had to be `type: "slack"`; file lookup accepted only Slack `ts` and optional `threadTs`.                                                  | Slack requests are unchanged. A Photon capability can park only its bound structured conversation. A Photon file lookup carries a structured message reference and rejects malformed, contradictory, or foreign scopes before parking.                                                                                |
| Message revisions            | Revision lookup derived Slack thread candidates from raw container and timestamp strings.                                                                         | Slack lookup and rendering are unchanged. Photon revisions require a structured message reference plus an authority-supplied set of registered session thread references. Raw container and message-string collisions do not authorize a mutation.                                                                    |
| Principal delivery sessions  | Only generic `principal` deliveries created recipient personal sessions.                                                                                          | Valid Photon DMs also create the recipient's personal session with surface `photon`. The existing delivery-store backlink limitation is recorded below.                                                                                                                                                               |
| Surface cache                | All ingested events could enter the Slack-shaped container cache and ambient flow.                                                                                | Slack is unchanged. Photon events are not inserted into the unscoped cache; supported structured revisions may be recorded through the registered-session resolver. This is a fail-closed boundary until the shared cache schema is surface-scoped.                                                                   |

## Destination and reference mapping

| QM concept      | Slack/default representation                                             | Photon representation                                                                                                                |
| --------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Teammate DM     | `type: "principal"`, canonical principal target, personal audience scope | `type: "photon"`, canonical recipient and personal audience scope, plus `ConversationReference`                                      |
| Group DM        | `type: "group"`, directory group target and group audience scope         | `type: "photon"`, canonical group identity and full participant set, group audience scope, plus `ConversationReference`              |
| Channel         | `type: "slack"`, Slack channel target and channel audience scope         | Unsupported; the caller must select an iMessage recipient or participant set                                                         |
| Message action  | Slack message `ts` in `react`, `delete`, or `editRef`                    | Existing action field plus `MessageTargetReference` scoped by provider, installation, line, conversation, message, and optional part |
| Context history | Slack `conversationTarget` or authorized channel                         | Capability-bound `ConversationReference`; the legacy target is retained only for the existing request envelope                       |
| Context file    | Slack `ts`, optional `threadTs`, optional name                           | Capability-bound `MessageTargetReference`, optional name; `threadTs` is rejected                                                     |

The Photon destination parser accepts only the two pinned provider names and exact JSON-safe reference fields. Provider, installation, line, conversation, message, and part identifiers remain separate. `projectId` and `maskedAddress` are retained when present but do not replace the provider/install/line/conversation authority key.

## Affected callers

- `src/api/app-helpers.ts` is the app-level reach adapter. It preserves directory-based Slack resolution and conditionally supplies the scoped Photon resolver to `resolveReachTarget`.
- `src/api/app-messaging.ts` is called by `src/api/routes/turns.ts` and `src/api/slack-core-client.ts` for delivery acknowledgement, by `src/api/routes/surface-cache.ts` and the Slack mirror for ingress, and by `src/api/routes/reach.ts`, control service, cron, trigger, loop, and orchestrator flows for reach. All existing calls omit a surface and therefore remain Slack/default unless their current destination is already a validated Photon destination.
- `src/api/routes/context.ts` serves `/v1/surface-context` and `/v1/surface-file`; its parked requests are consumed by the existing surface-context puller and provider plugin boundary.
- `src/core/message-revisions.ts` is called during surface ingress and by orchestrator turn-end reconciliation. Ingest-time Photon handling uses only the new structured path; turn-end reconciliation remains Slack-specific.
- `src/reach/reach.ts` is also called directly by `src/core/orchestrator/surface-tools.ts`. That caller has no Photon resolver or surface selection and retains existing behavior.
- `src/directory/directory-store.ts` is not changed. WT05 uses its additive `upsertGroup` path and does not call the destructive snapshot replacement methods.

## Exact shared changes needed at integration

1. Add the structured Photon destination, conversation, message, and ingest fields to the integration-owned declarations in `src/types.ts`, `src/surface-cache/types.ts`, and `src/api/app-types.ts`. Add `photonDestinations?: PhotonDestinationResolver` to `AppDeps` and compose the durable WT07 resolver in `src/wiring.ts`. WT05 uses local narrowed types so it does not edit frozen shared contracts.
2. Preserve and validate Photon fields in `src/api/capability-destination.ts`. Its current candidate projection retains only `type`, `target`, and `audienceScopeId`, so a selected Photon candidate loses its authority-bearing reference and correctly fails WT05 validation.
3. Extend `src/api/routes/reach.ts` to parse an explicit surface and carry the validated current Photon destination through attachment preflight. Final reach already receives the current capability destination and WT05 infers Photon from it, but attachment preflight resolves without that surface and the route still requires a named target for reactions. Permit a current-conversation reaction only for a validated Photon destination.
4. Have the WT08 inbound/session path persist `providerMessage` on transcript user entries and pass structured revision events to `ingestSurfaceEvents(..., "photon")`. Supply `sessionThreadRefs` from WT07's durable routing/session authority. Without both pieces, Photon revision events are intentionally ignored.
5. Surface-scope the cache keys and durable schema before allowing Photon events into `SurfaceCache`; otherwise identical raw container/message strings from Slack and Photon can collide. Until that change, WT05 returns zero cached Photon events and does not run Slack ambient policy over them.
6. Extend the memory and PostgreSQL delivery stores' `recordRecipientThread` and `listByRecipientThread` rules to recognize validated Photon DMs by canonical recipient. The present store implementations accept only `destination.type === "principal"`, so WT05 creates the correct Photon personal session but the delivery backlink is not yet persisted.
7. Have WT09 consume only validated `type: "photon"` destinations and their structured `providerMessage` references for send, reaction, edit, and unsend operations. Bare `target`, `react.messageTs`, `delete.messageTs`, and `editRef` remain compatibility fields, not provider authority.
