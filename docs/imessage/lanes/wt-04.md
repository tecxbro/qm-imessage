## Credential acquisition and lifecycle ownership

`createConnectionManager().replace(line, credentials)` constructs the real pinned client from an explicit `address` and bearer `token` associated with the supplied installation/line. It neither treats a management login token as a runtime token nor derives an Advanced token from a Spectrum project secret. Actual acquisition/decryption and the approved installation-to-server binding must be supplied by WT02/integration. No live credentials were obtained, loaded, renewed, or exercised in this lane.

Spectrum receives one explicit public `imessage.config({ clients: [{ address, token, phone }] })` configuration. This retains the exact phone on conversation creation, lookup, target resolution, attachment fetch, and returned-message checks. Explicit Spectrum clients do not auto-renew. Renewal calls `replace` with newly acquired credentials; replacing a line follows the same stop-before-construction path. Advanced uses the public gRPC `createClient` constructor, TLS, a 30-second unary timeout, and disabled unary retry/automatic random idempotency. Supported Advanced writes use a stable hash of the logical key plus provider, installation, line, conversation, and any multipart subset as their documented `clientMessageId`.

A manager serializes transitions. A module-local owner reservation excludes simultaneous managers for the same installation/line, including attempts to switch between Spectrum and Advanced while the old connection still exists. A connection permits one intake consumer. This reservation is disposable process-local coordination, **not a distributed lease**. Multi-instance activation requires an approved durable ownership contract and integration binding; this lane does not claim that absent contract is satisfied.

Shutdown invalidates new work, closes streams, and waits for already-started handoffs. A 30-second default drain deadline reports `PROVIDER_INTAKE_DRAIN_TIMEOUT` while retaining ownership. Stop can be retried after the late handoff finishes; replacement cannot overlap the stalled owner. A late client-construction result is closed before it can become current. A provider write that already returned a valid receipt remains confirmed even if shutdown occurred while it was in flight; an unknown result remains ambiguous.

## Recovery and observation limits

Advanced intake opens all four public live streams before requesting `events.catchUp(since)` from the durable checkpoint. Every event is durably captured through the frozen receipt-store port before downstream handoff. The bounded replay staging set is disposable and re-derived on restart; it never replaces the durable inbox. Overlapping live/replay events retain identical keys and payloads. Conflicts stop recovery. All captured replay inputs are available before sorted handoff begins.

Defaults are 4,096 unique replay events, 16 MiB of normalized replay data, and a 30-second catch-up deadline. Overflow, invalid/regressed cursors, missing completion, live-stream termination, and timeout are explicit failures. The event that exceeds the staging bound remains durably captured. Recovery does not silently truncate the range. A larger backlog requires approved durable discovery or deliberate recovery configuration.

`completion` reports the observed catch-up head separately from inbox envelopes. It does not synthesize a sequenced event or advance a checkpoint. WT04 calls **no** receipt completion/rejection/checkpoint mutation. The pinned declarations specify increasing sequences and public decoders can omit unrecognized frames; they do not certify that every integer is representable in the frozen contiguous-store contract. A gap or changed sequence scope requires an integration amendment, never a skipped cursor or invented event. Initial boundaries must still obey the frozen lowest-captured-sequence rule in WT08/WT03.

Spectrum intake can durably capture the public events it exposes, but its internal replay cursors are not public or durably controllable by WT04. It suppresses some native events and cannot claim complete restart recovery. Native recovery requires the Advanced intake mode with an independently acquired, correctly scoped credential; there is no second intake behind a Spectrum connection.

`getPoll` validates exact chat/poll scope and propagates read errors while returning the frozen `PhotonPollState`. `observeAdvancedMessage` validates exact line, chat, and message identity and returns only a plain, explicitly inconclusive observation. It produces no reconciliation success: a matching message, text, current state, or missing history does not correlate a logical write. There is no positive observation/reconciliation contract adoption without C01/C02.

## Public declaration compatibility finding

The Advanced public types compile against 2.1.0. Spectrum 12.8.0's published iMessage generic definition fails its own `AnyPlatformDef` constraint under the pinned TypeScript 5.9.3 settings. The documented `imessage.config({clients: ...})` resolves to `never`, and the documented `Spectrum` construction produces TS2345/TS2769. Disabling `skipLibCheck` also exposes the upstream `events: undefined` constraint failure and bundled declaration errors.

`compatibility.ts` confines the workaround to the exact documented public constructors/narrowers, invoked through `Reflect.apply`, with runtime shape checks and a narrow local projection of the public methods. It never accesses `.client`, `__internal`, private SDK state, fabricated cursor options, or credential bridges. The executable TypeScript probe records the actual failed declaration example rather than claiming generic declaration compatibility. The separate smoke test constructs, narrows, and closes real pinned clients against an offline localhost endpoint. This establishes local construction/runtime-surface evidence only. Integration must review this compatibility workaround or approve corrected pins; no frozen package files were changed.
