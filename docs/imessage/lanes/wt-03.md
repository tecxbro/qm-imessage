## Persisted channel mechanics

The PostgreSQL implementation covers every frozen r2 state port without adding an authoritative QM session, task, memory record, approval decision, schedule, or business/execution queue:

- private installation revisions and verified-address challenge state;
- provider conversation to QM session bindings and provider message-part to QM entry bindings;
- attachment lifecycle references;
- recoverable event envelopes, fenced receipt claims, terminal rejection or completion, and contiguous line checkpoints;
- logical delivery reservations, provider attempts, per-part state, exact confirmed provider identities, retryable failure, ambiguity, and explicit reconciliation;
- ordered durable text-stream chunks;
- poll references, restart-safe public card handles, and scoped single-use action bindings.

All serialized top-level records use envelope version `1`. Reads reject unknown versions, malformed or noncanonical payloads, JSON values PostgreSQL cannot preserve, delivery-parent/part disagreement, stream/chunk disagreement, and plaintext installation credentials. Installation status may persist credential paths or ciphertext supplied by the frozen contract, but not access tokens, project secrets, device codes, or unknown private fields.

## Schema and indexes

The migration creates 15 tables under `qm_photon_state`. Every provider-derived primary key contains the full available provider, installation, line, and conversation scope before its resource identity. Provider event IDs are additionally line-scoped; an event whose frozen identity has no line uses an internal installation-scoped empty sentinel that cannot collide with a valid nonempty line ID. Logical delivery uniqueness is based on the stable idempotency key; operation and attempt identity have a separate full-scope unique index.

Indexes support:

- bounded receipt discovery by tenant, state, sequence, capture time, and event ID;
- expired processing-claim lookup;
- bounded delivery discovery by tenant, state, update time, and logical key;
- exact operation-attempt uniqueness;
- QM entry reverse lookup;
- unverified challenge expiry and unconsumed action expiry.

Foreign keys keep message-part lookup rows, delivery parts, and stream chunks attached to their parent channel record. The migration is registered through QM's checksum ledger and reapplying the exact source is a no-op; source drift after application is rejected.

## Transactions and concurrency

Receipt capture is conflict-aware and does not import claims or terminal states. Claims use row locks, monotonically increasing fences, and caller-supplied lease timestamps. Exact lease expiry permits takeover; stale fences cannot finish a replacement claim. Sequenced success and sequenced rejection take a transaction-scoped line lock, validate the active claim, validate exact next-sequence continuity, update the checkpoint, and terminate the receipt in one transaction. The initial cursor refuses to skip any earlier captured sequence in the same scope. Unsequenced receipts use separate terminal methods and cannot advance the cursor.

Delivery reservation serializes on the logical operation scope. Dispatch and completion use row locks, entity versions, and dispatch fences. A retry is allowed only after a retryable failure, retains confirmed children exactly, and reserves only unresolved logical part indexes. Ambiguous outcomes are never retried by this store and can leave that state only through matching explicit reconciliation evidence. Missing or contradictory evidence fails before parent or child state changes.

Installation, challenge, poll, card, stream, and action transitions use row locks or compare-and-set predicates where the frozen port exposes a version. Action consumption verifies the complete actor, resource, revision, action, session, conversation, expiry, and one-use state in one transaction.

## Database boundary

The migration creates two `NOLOGIN` group roles:

- `qm_photon_adapter` receives schema usage and `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on the 15 channel-state tables only.
- `qm_photon_core_link` receives schema usage and `SELECT`, `INSERT`, and `UPDATE` only on chat bindings, message bindings, and their part lookup table.

`PUBLIC` receives no schema or table privileges. Neither group role can migrate the database, create schema objects, or read unrelated QM tables. Deployment must grant the appropriate group role to separate login identities or use an equivalently isolated role setup. The privileged migration identity must not be reused by either runtime path.

## Retention and migration operations

The frozen ports define state transitions but no purge API or retention interval. This lane therefore performs no scheduled cleanup and invents no retention policy. Expired challenges and action bindings become unusable based on their persisted timestamps; terminal receipts, delivery evidence, bindings, poll references, card handles, and finalized stream records remain durable until an integration-approved retention contract owns their deletion. In particular, this lane does not create a scheduler or cleanup queue.

Apply through the central QM migration runner. Reapplying the same checksum is safe. A failed first application is rolled back by the existing migration transaction and is safe to retry after the cause is fixed. There is no automatic down migration. Before activation, rollback is removal of the unactivated registration and, if the migration was applied only to an isolated disposable database, explicit removal of `qm_photon_state` and its ledger row by an operator. After activation or persisted production data, do not drop the schema or edit the ledger; roll forward with a new reviewed migration and preserve the evidence.
