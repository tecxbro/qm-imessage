## Repair

The imported candidate broadened the existing Slack `recipientThreadRef` graph to Photon deliveries. That conflated a QM session-thread reference with the frozen Photon backlink record and could not prove that the supplied session belonged to the delivery's canonical recipient.

The two delivery stores now implement the frozen `PhotonDmBacklink` contract directly. A record is accepted only when the current delivery is a fully validated Photon DM and both `recipientPrincipalId` and the complete `ConversationReference` exactly match that destination. The first accepted record returns `recorded`, an exact retry returns `duplicate`, and an absent delivery, mismatched record, malformed destination, group, Slack delivery, or conflicting stored state returns `conflict`. Reads validate the persisted record against the current delivery again and otherwise return `undefined`.

The in-memory store holds a distinct cloned backlink value. The PostgreSQL store locks the delivery row while validating and writing, so destination changes and competing records cannot cross the authorization check. Store recreation proves the PostgreSQL record is durable.

The coordinator allocated migration `delivery/store/0007-photon-dm-backlinks` in the R08-owned PostgreSQL delivery store. It adds one nullable JSONB column, `deliveries.photon_dm_backlink`, which stores exactly `{ recipientPrincipalId, conversation }`. It does not reuse `recipient_thread_ref`.

The original `recordRecipientThread` and `listByRecipientThread` implementations remain principal-only. Their acknowledgement, ordering, and filtering behavior is unchanged, preserving the Slack delivery graph and its existing durability.
