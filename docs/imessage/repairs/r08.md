## Reproducer and repair

`createDeliveryStore().recordRecipientThread` and `createPostgresDeliveryStore().recordRecipientThread` rejected every delivery whose destination type was not `principal`. Their paired `listByRecipientThread` implementations applied the same principal-only filter. WT05 can create the correct Photon personal session, but a confirmed Photon DM therefore had no delivery backlink in that session.

`supportsRecipientThread` is the shared gate used by both stores. It retains the original principal behavior and accepts a Photon destination only when `isPhotonDestination` validates the complete destination and `conversationKind` is `dm`. Photon groups and malformed stored JSON fail closed.

The PostgreSQL record path reads and validates the current JSON destination. Principal rows retain the original type predicate. A validated Photon DM is updated only while its destination remains byte-equivalent as JSONB to the value that passed validation. The compare-and-set prevents a destination mutation between validation and update from recording or acknowledging the delivery.

The PostgreSQL list path selects only principal and Photon-DM candidates, validates each candidate through `supportsRecipientThread`, and uses descending `(created_at, id)` keyset pagination until it has collected the requested number of valid rows or exhausted the candidates. It then returns the page in chronological order. A malformed Photon candidate therefore cannot consume a limited result slot.

No queue, migration, delivery state machine, retry policy, expiry rule, event notification, or transcript was added.

## Remaining limitations and coordinator deltas

`recipientThreadRef` remains opaque to the delivery store. The store does not receive a canonical recipient binding and does not authorize a session. The current `recordPrincipalDelivery` caller derives the recipient from the validated delivery destination but accepts the thread reference without an authority-derived binding, so this repair does not claim wrong-recipient rejection. It also creates or updates the session before the store compare-and-set, which can leave a session-side effect if a concurrent destination mutation makes the backlink update fail. The coordinator must assign a shared caller or interface delta that obtains the thread from the verified recipient's durable binding, rejects a binding for another recipient before session mutation, and does not treat a failed store compare-and-set as a recorded backlink. That assembled behavior needs a composition-level regression test.

The supplied repair classification and the WT05 handoff require the existing `recordRecipientThread` and `listByRecipientThread` methods to recognize validated Photon DMs. `docs/imessage/repairs/contracts.md` instead sketches a separate `recordPhotonDmBacklink` and `photonDmBacklink` interface. The coordinator should replace that Delivery backlinks section with the existing-method contract and `supportsRecipientThread` semantics. No backlink migration is needed for this implementation.

The supplied repair text names `test/photon-repair-r08-backlinks.test.ts`, while the coordinator ownership record assigns `test/photon-delivery-backlinks.test.ts` and `test/postgres-photon-delivery-backlinks.test.ts`. This repair uses the coordinator-owned paths. The coordinator should align the dispatch text or ownership record and add the PostgreSQL repair test to the `test:pg` CI list.

Store recreation proves that the backlink is durable and visible through a new delivery-store instance. The test does not restart the PostgreSQL server process, so database-process restart remains not run rather than passed.
