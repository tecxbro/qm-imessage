## Reproducer

The current store has this durable sequence:

1. reserve creates a reserved parent and reserved child rows.
2. markDispatched(operation, expectedVersion) changes unresolved work to dispatched and increments dispatchFence.
3. The provider sends a part.
4. complete(operation, dispatchFence, outcome) writes the terminal outcome.

The gap is observable with a sequential multipart send: a provider can accept a part, then the worker can crash before terminal completion. The accepted part is not durably recorded before the next provider send, and there is no owner or lease proving which worker may continue. A restarted worker has no safe per-part progress boundary. A late result is guarded only by state and fence, not by a live owner claim, expiry, or exact attempt identity.

The same failure mode exists for a worker that stops after dispatch: the row remains dispatched without a durable expiry decision. Legacy rows created before lease columns exist also have no claim. They must not be treated as safely completable or safely retryable; known confirmed parts must be retained and unresolved work must become ambiguous through recovery.

## Implemented production changes

Within plugins/chassis/src/photon-state/deliveries.ts, the implementation now:

- acquireDispatch locks the parent, requires reserved state and expected version, validates the full operation and payload, installs a new owner/expiry and fence, marks unresolved parts dispatched, and persists parent and children atomically.
- renewDispatch locks the parent, requires the exact owner and fence and a still-live claim at injected now, then extends the lease. An expired claim cannot be resurrected.
- recordConfirmedPart locks the parent, requires the exact live claim and current attempt, validates the logical index and conversation, rejects conflicting or reused provider identity, and persists the confirmed child before the next multipart provider send. An identical duplicate confirmation at the same logical index is idempotent.
- expireDispatch locks the parent, validates expiry at the injected canonical time, and transitions abandoned or legacy no-lease work conservatively to ambiguity while retaining every confirmed part.
- complete accepts DeliveryDispatchClaim and now, requires a live claim plus exact operation, payload, and attempt identity, parses the terminal outcome, and reuses completedDeliveryRecord for receipt and confirmed-part validation.
- discoverRecoverable provides bounded, stable scope pagination using DeliveryRecoveryCursor, normalizes database ordering to milliseconds without losing cursor position, verifies relational scope against parent JSON, and returns parent/child-consistent records under row locks.
- read also locks the parent before reading children so it observes one valid pre-write or post-write representation rather than mixing snapshots.
- the legacy markDispatched entry point fails closed, and the old fence-only complete form returns false, until the coordinator publishes the shared lease-aware port and migrates every caller.

All parent/child updates for one transition must remain one transaction. Provider progress must be durable before another logical multipart part is sent. Existing retry semantics remain: retry only known retryable failures, use a new operation/attempt identity, and send only unresolved indexes. Ambiguous work remains reconciliation-first.

## iMessage-specific rationale and boundaries

WT04 records that Spectrum multipart sends are sequential and may return Message or undefined; an undefined message-producing result is ambiguous. Advanced multipart sends are atomic and its retry behavior is disabled (docs/imessage/lanes/wt-04.md:11-35). The shared iMessage contract requires exact logical part identity, preservation of confirmed parts, reconciliation-first handling of ambiguity, and no unsupported success (docs/imessage/contracts.md:11-72).

Therefore R04 supplies the durable control-plane boundary needed by the provider adapter; it does not prove provider acceptance, native embedding, or device delivery. Provider authentication, receipt interpretation, and provider progress remain WT04/R11 responsibilities. There are currently no production provider callers of createPhotonDeliveryStore; its construction is wired through plugins/chassis/src/photon-state.ts:22,533-547, so the new port is an integration seam rather than an already exercised end-to-end path.

Legacy dispatched rows with nullable lease fields must be handled conservatively: no ordinary completion, no blind retry, preserve known confirmed parts, and reconcile or mark ambiguous. No retention, purge, SDK upgrade, or native correlation behavior is introduced by R04.
