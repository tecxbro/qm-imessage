# R13 repair contribution provenance

## Why this repair exists

Checkpoint integration originally required every lane-owned path in the final candidate to match the captured lane commit. That is correct until a reviewed post-merge repair changes the path. Without separate repair provenance, a legitimate Photon/iMessage correction is indistinguishable from unreviewed integration drift, and a candidate that passes integration verification cannot be used to prepare Wave B.

This is workflow support for the downstream Photon channel integration. It does not change QM runtime, Slack, web, scheduling, model, memory, approval, or persistence behavior.

## Reproducer

1. Create two repair branches from the captured preparation commit.
2. Change different lane-owned paths on the two sibling branches.
3. Merge both exact repair commits into an integration candidate.
4. Record the original lane commits and the repair commits in the checkpoint.
5. Run integration verification and then Wave B preparation against the same candidate.

Before R13, `LANE_CONTRIBUTION_DRIFT` or `WAVE_LANE_CONTRIBUTION_DRIFT` rejects the repaired path even when the final blob is exactly the reviewed repair result.

## Changed symbols

The old integration and Wave checkpoint loops compared every lane path directly from `laneCommit` to the final candidate.

The new shared API is `validateRepairProvenance`. It validates `repairContributions` records with `repairId`, `baseCommit`, and `commit`; derives changed paths from Git; binds them to the frozen repair ownership and external dispatch record; resolves the final contribution per path; and exposes `requireOriginalPath` for the lane-to-repair base transition. The dispatch filename is resolved relative to the actual `git rev-parse --git-common-dir` result. The dispatch coordinator identity is checked against the repair coordinator while the original `imessage/integration` identity remains authoritative for checkpoint verification and Wave B preparation. `repairProvenance` is the common verifier entry point used by integration verification and later-wave preparation. `verifyCheckpointScope` also receives the repair-owned mandatory test union.

Paths without a repair retain the original direct lane comparison. Paths with a repair must preserve the lane blob and mode at the repair base and match the selected repair commit in the final candidate, including deletion and rename endpoints. Independent disjoint siblings are accepted. Incomparable same-path siblings are rejected unless a declared resolving contribution descends from both, explicitly depends on both, and owns the path. Ancestry alone does not review an overlap: every same-path predecessor must be present in the later contribution's declared dependency chain.

Post-merge lane attribution checks repair provenance first. An unchanged original-lane path remains attributed to its lane. A changed original-lane path becomes integration-owned only when it matches the explicit integration allowlist. The WT01-WT06 handoff documents have a narrower rule: every original byte and the file mode must remain intact, and the appended bytes must begin with the exact `## Accepted checkpoint 1 corrections` section marker. A rewritten handoff fails even when the integration allowlist otherwise matches its path.

Immutable checkpoints are now compared by Git blob identity instead of trimmed text, so byte changes cannot pass as the historical checkpoint.
