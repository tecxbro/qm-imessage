## Reproducer

A capability containing a valid Photon candidate could select it by key or by `defaultDestinationKey`, but `stripCandidate` projected only `type`, `target`, and `audienceScopeId`. The resulting value no longer contained the provider, installation, line, conversation, canonical principals, DM or group identity, or optional provider-message reference. It therefore was not a valid Photon destination at the next boundary. A malformed array entry could also throw during key lookup because signed capability parsing checks that `destinations` is an array but does not validate every entry.

The repair-specific test constructs valid DM and group destinations with `createPhotonDestination`, adds the capability menu fields, and resolves them through each supported selection path. Against the old implementation, 7 of 9 tests failed: explicit and default candidates lost structured identity, malformed Photon candidates were accepted as generic three-field destinations, and a malformed menu entry threw during lookup.

## Symbol changes

- Old `stripCandidate` returned a three-field `Destination` for every candidate.
- New `projectPhoton` first calls `isPhotonDestination`, then reconstructs the destination with `createPhotonDestination` from an explicit allowlist.
- New `stripCandidate` uses that checked projection only when `type` is `photon`; its non-Photon projection is unchanged.
- New `findCandidate` ignores malformed menu entries while preserving exact string-key matching.
- `resolveCapabilityDestination` now applies the same checked Photon projection to explicit selection, default selection, and the direct capability fallback. Malformed Photon data returns `{ ok: false }`.

No new shared API is proposed. The implementation reuses `PHOTON_DESTINATION_TYPE`, `isPhotonDestination`, and `createPhotonDestination` from `src/surfaces/photon-destinations.ts`. The current `Destination`, `CandidateDestination`, and `CapabilityClaims` declarations typecheck without a shared declaration change.

## Why iMessage needs this

The frozen Photon source describes iMessage routing as conversation- and line-specific, including cases where multiple dedicated lines require an explicit serving line. A bare conversation target cannot retain that authority boundary. The optional provider-message reference must also remain scoped to the same provider, installation, line, and conversation so a message action cannot cross conversations.

The implementation was checked against the locked `docs/imessage/sources/photon/spectrum-ts/providers/imessage/connection-and-routing.md` and `docs/imessage/sources/photon/spectrum-ts/providers/imessage/messaging-features/message-metadata.md` snapshots selected through `docs/imessage/source-lock.json`.

## Allowlist and failure behavior

The Photon projection retains only the validated conversation, conversation kind, canonical principal IDs, audience scope, matching recipient or group identity, and optional same-conversation provider-message reference. Capability menu fields and unrelated authority or execution metadata are discarded. In particular, selection does not preserve `key`, `label`, `onBehalfOf`, reaction, approval, actor, execution, or unknown fields.

The focused coverage includes explicit DM selection, default group selection, direct Photon fallback, an absent explicit key, a foreign provider-message reference, invalid principals, an invalid audience scope, missing line identity, unknown metadata, and byte-identical representative Slack projections.

## Remaining limitations and shared deltas

No shared edit is authorized or required for the R06 projector to typecheck. Integration still needs these coordinator-owned deltas before a structured Photon candidate can reach it end to end:

- `src/types.ts` must represent the structured Photon destination and candidate fields on the shared declarations, including `TurnRequest.deliveryCandidates`.
- `src/surface-cache/types.ts` and `src/api/app-types.ts` must receive the previously requested structured Photon fields, and `AppDeps` must expose `photonDestinations?: PhotonDestinationResolver`.
- `src/wiring.ts` must compose the durable Photon resolver supplied by the routing owner.
- `src/core/orchestrator/turn-helpers.ts` and `src/core/orchestrator.ts` must carry an already validated Photon destination through `deliveryCandidatesFor` and the `defaultDestination` projection. They currently reconstruct only a target, label, type, and audience scope, which erases Photon identity before R06 receives it. The integration change must retain an explicit allowlist rather than spread arbitrary input metadata.

The R06 guardrail and implementation intentionally do not grant that authority during selection.
