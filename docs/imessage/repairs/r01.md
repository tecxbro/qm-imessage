## Reproducer

`PhotonCliInstallationService.#loadOrCreate` created its first `InstallationRecord` at version `0`. The existing PostgreSQL installation port accepts creation only at version `1`, so the first real setup could not be stored. Later setup transitions retain private management and runtime fields, including `projectSecret`, while the existing database validator accepts a normal installation record only when runtime contains `credentialCiphertext`.

The frozen repair contract separates the private `InstallationRecord` service view from `PhotonInstallationCiphertextRecord`, the five-field encrypted database view. The complete private service record is authenticated and encrypted.

## Changed symbols

- `PhotonCliInstallationService.#loadOrCreate` now creates version `1`; `#transition` still increments `current.version` by one.
- `SecretKey`, `HKDF_SALT`, `deriveConnectorKey`, `encryptSecret`, and `decryptSecret` moved byte-for-byte from `src/connectors/connector-client-store.ts` to `plugins/chassis/src/secret-box.ts`. The old module re-exports the public functions and type, preserving existing QM imports and behavior.
- `createEncryptedPhotonInstallationStore` implements the frozen service-versus-database boundary using the coordinator-owned `PhotonInstallationCiphertextRecord`, `PhotonInstallationCiphertextStore`, and `PhotonInstallationStoreAdapter` declarations from `plugins/photon/src/ports.ts`. No competing R01 declaration remains.
- `PhotonInstallationSecretCodec` exposes the current `wrappingKeyId`, encrypts with the current key, and receives each stored wrapping-key ID during decryption so composition can select retained historical keys before a compare-and-set rewrite.
- The adapter encrypts the complete validated `PrivateInstallationStatus`, including supported management, device-code, project-secret, and transitional credential-ciphertext fields. The clear database record has exactly the five frozen fields.
- The encrypted envelope binds record kind, installation ID, owner revision, entity version, and wrapping-key ID. Decryption, schema, context, key-ID, tamper, ciphertext-swap, and whole-row-swap failures expose only `PHOTON_INSTALLATION_SECRET_INVALID`. Invalid service writes expose only `PHOTON_INSTALLATION_SERVICE_SECRET_INVALID`.

4. In R15 composition, derive Photon installation keys from persistent host-private material with the explicit purpose `photon-installation`, retain a key-ID-indexed decryption keyring, provide a stable current non-secret `wrappingKeyId`, and construct one `createEncryptedPhotonInstallationStore` private service view. Inject that adapter into `PhotonCliInstallationService` and every other private installation consumer, including `PhotonAuthorizationDeps.installations`. Missing persistent key material, current key ID, or a referenced historical key must block composition; no random restart key or messaging token is an acceptable fallback.

The assembled codec boundary is:

```ts
const installationStore = createEncryptedPhotonInstallationStore(state.stores.installations, {
  wrappingKeyId: currentInstallationKey.id,
  encrypt: (value) => encryptSecret(value, currentInstallationKey.key),
  decrypt: (value, wrappingKeyId) => decryptSecret(value, installationKeys.require(wrappingKeyId)),
});
```

`currentInstallationKey` and `installationKeys` are required composition inputs backed by persistent host-private material, not new globals.
