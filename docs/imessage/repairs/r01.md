# R01 encrypted installation storage

## Reproducer

`PhotonCliInstallationService.#loadOrCreate` created its first `InstallationRecord` at version `0`. The existing PostgreSQL installation port accepts creation only at version `1`, so the first real setup could not be stored. Later setup transitions retain private management and runtime fields, including `projectSecret`, while the existing database validator accepts a normal installation record only when runtime contains `credentialCiphertext`.

The coordinator-frozen repair contract supersedes the earlier runtime-field-only suggested adapter. Its service view is `InstallationRecord`, while its database view is a distinct `PhotonInstallationCiphertextRecord` containing only clear installation ID, owner revision, entity version, wrapping-key ID, and ciphertext. The complete private service record is authenticated and encrypted.

This blocks iMessage activation because Photon installation state cannot cross the setup-service-to-PostgreSQL boundary or survive a restart without either persisting private state in cleartext or failing strict validation.

## Changed symbols

- `PhotonCliInstallationService.#loadOrCreate` now creates version `1`; `#transition` still increments `current.version` by one.
- `SecretKey`, `HKDF_SALT`, `deriveConnectorKey`, `encryptSecret`, and `decryptSecret` moved byte-for-byte from `src/connectors/connector-client-store.ts` to `plugins/chassis/src/secret-box.ts`. The old module re-exports the public functions and type, so existing QM callers retain their import path and behavior.
- `PhotonInstallationCiphertextRecord`, `PhotonInstallationCiphertextStore`, and `PhotonInstallationStoreAdapter` implement the frozen service-versus-database boundary.
- `PhotonInstallationSecretCodec` exposes the current `wrappingKeyId`, encrypts with the current key, and receives each stored wrapping-key ID during decryption so composition can select retained historical keys before a CAS rewrite.
- `createEncryptedPhotonInstallationStore` encrypts the complete validated `InstallationRecord` on every write and decrypts only private service reads. The clear database-facing record has exactly the five frozen fields.
- The encrypted envelope binds record kind, installation ID, owner revision, entity version, wrapping-key ID, and the complete installation record. Project, status, line, authorization, management, and runtime fields remain inside authenticated ciphertext. Decryption, schema, context, key-ID, tamper, ciphertext-swap, and whole-row-swap failures expose only `PHOTON_INSTALLATION_SECRET_INVALID`. Invalid service writes expose only `PHOTON_INSTALLATION_SERVICE_SECRET_INVALID`.

2. Promote the frozen `PhotonInstallationCiphertextRecord`, `PhotonInstallationCiphertextStore`, and `PhotonInstallationStoreAdapter` declarations from `plugins/photon/src/setup/installation-store.ts` into coordinator-owned `plugins/photon/src/ports.ts`, then update the R01 module to import them.
3. Change coordinator-owned `PhotonStateStores.installations` and its PostgreSQL implementation in `plugins/chassis/src/photon-state.ts` from `InstallationStorePort` to `PhotonInstallationCiphertextStore`. Add strict ciphertext-record encoding and decoding in `plugins/chassis/src/photon-state-records.ts`: accept exactly `installationId`, `ownerRevision`, positive safe-integer `version`, nonempty `wrappingKeyId`, and nonempty `ciphertext`; preserve create-at-1 and compare-and-set version rules. Convert the existing installation assertions in `test/photon-state-postgres.test.ts` from full service records to the ciphertext record shape, including its restart read at the current line 607.
4. Grant and add `test/photon-repair-r01-postgres.test.ts`, or place equivalent integration-owned assertions in the checkpoint PostgreSQL test, to run `PhotonCliInstallationService` through `createEncryptedPhotonInstallationStore(state.stores.installations, codec)`, inspect raw JSON for exactly the five clear fields, and verify restart, stale CAS, wrong and retained keys, CAS rewrapping, tamper, ciphertext and row swaps, safe errors, and redaction.
5. In R15 composition, derive Photon installation keys from persistent host-private material with the explicit purpose `photon-installation`, retain a key-ID-indexed decryption keyring, provide a stable current non-secret `wrappingKeyId`, and construct one `createEncryptedPhotonInstallationStore` private service view. Inject that adapter into `PhotonCliInstallationService` and every other private installation consumer, including `PhotonAuthorizationDeps.installations`. Missing persistent key material, current key ID, or a referenced historical key must block composition; no random restart key or messaging token is an acceptable fallback.

After the PostgreSQL store type is converted, the assembled codec shape is:

```ts
const installationStore = createEncryptedPhotonInstallationStore(state.stores.installations, {
  wrappingKeyId: currentInstallationKey.id,
  encrypt: (value) => encryptSecret(value, currentInstallationKey.key),
  decrypt: (value, wrappingKeyId) => decryptSecret(value, installationKeys.require(wrappingKeyId)),
});
```

`currentInstallationKey` and `installationKeys` are required composition inputs backed by persistent host-private material, not new globals. The coordinator must use `decryptSecret` in the `decrypt` callback; the shape above names the callback boundary, not a new credential manager.

## Remaining limitations

R01 supplies the version fix, ciphertext adapter, shared encryption relocation, and offline tests. It does not wire shared composition, create the PostgreSQL ciphertext-store producer and validator, provision host key material, or own the final PostgreSQL acceptance test. Those coordinator-owned changes remain blockers before this is integrated or activated. No live Photon authentication, provider acceptance, message delivery/read, or device behavior was exercised.
