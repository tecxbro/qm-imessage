## Reproducer and old behavior

The old Spectrum `createSpectrumProviderClient().deliver()` multipart branch called `space.send(part)`, validated the returned message with `spectrumResult()`, and appended the confirmed part only to the local `confirmedParts` array. It immediately started the next provider write. Blocking or failing durable storage was impossible because no in-process progress port was present.

Spectrum's frozen `content/composing-content` source states that composed items are sent sequentially as separate provider messages. A process failure or owner, fence, line, or audience change between those calls could therefore leave the provider with part one while durable state still allowed part two to be attempted without a persisted part-one checkpoint.

## New behavior and symbols

`PhotonDispatchProgress` is represented locally in `clients.ts` until the coordinator promotes the shared contract. `dispatchProgress()`, `beforeProviderWrite()`, and `confirmProviderWrites()` keep callback functions out of serialized operations and provider requests.

Spectrum multipart now returns `unsupported` with reason `durable-multipart-progress-unavailable` before `runner()`, space lookup, or provider side effects when the callback is absent. For each unresolved logical part, it awaits `beforeSend([logicalPartIndex])`, checks the connection, performs one `space.send()`, validates the provider receipt, retains that evidence in memory, and awaits `confirm(receipt)` before continuing. Callback rejection is wrapped as an ordinary local error, so the existing `runner()` returns an ambiguous outcome rather than misclassifying a storage or authority failure as an SDK rejection.

Advanced multipart remains one provider-atomic `sendMultipart()` call. When progress is supplied, it checks all selected logical indexes in one `beforeSend()` call and confirms every validated returned receipt after that one provider result. It does not split the operation into text or attachment writes, and absence of the optional callback preserves the existing atomic provider path.

## Coordinator deltas

The coordinator-owned `plugins/photon/src/ports.ts` needs an exported `PhotonDispatchProgress` with `beforeSend(logicalPartIndexes: readonly number[]): Promise<void>` and `confirm(part: ConfirmedMessagePart): Promise<void>`, plus additive `progress?: PhotonDispatchProgress` on `PhotonDeliveryDispatch`. Once promoted, `clients.ts` should import that shared type and remove its temporary local structural mirror.

R16 composition must supply the callback for Spectrum multipart. `beforeSend` must enforce the exact live dispatch owner and fence, line lifetime, and approved current audience through R04 and R14 authority. `confirm` must call R04's transactional confirmed-part write and reject stale or conflicting receipts. No production no-op or in-memory replacement is valid.

The two Spectrum multipart cases in `plugins/photon/test/provider.test.ts` must receive explicit progress test doubles while retaining their existing malformed-result and lost-response assertions. A separate missing-progress assertion already lives in R11's owned test.

The supplied R11 assignment and the frozen repair contract differ in two places. R11 follows the more specific supplied assignment by gating every Spectrum `message.multipart` operation without progress, while `docs/imessage/repairs/contracts.md` currently says the callback is required only when more than one logical part remains. The assignment also requires Advanced to check all selected indexes before its atomic write and persist all returned receipts afterward, while the frozen contract says provider-atomic multipart calls do not fabricate part callbacks. The coordinator must resolve these statements and update the frozen contract or the assembled R11 code before integration; the current repair must not be merged as though the conflict were absent.

Canonical iMessage documentation may describe Spectrum multipart as progress-gated after the shared port and composition land. No frozen source, WT04 handoff, shared fixture, validator, migration, or canonical document was changed by R11.

## Remaining limitation

A crash can still occur after remote provider acceptance and before the local receipt transaction commits. That state remains ambiguous and reconciliation-first. This repair provides ordered durable handshakes between sequential writes; it does not establish exactly-once delivery, provider idempotency for Spectrum writes, live provider acceptance, delivery, read state, native rendering, or device observation.
