## Reproducer

1. Link one Photon conversation to QM session A.
2. Bind a delivered provider message part and an approval action to A.
3. Change the conversation selection to session B.
4. Reply to the old A message or resolve the old A approval.

Previously, `authorize()` read the current conversation binding first and used B for the reply. The approval path compared its A-bound action to B and denied it. A new ordinary message correctly belongs to current selection B, but historical replies and actions must retain the QM session recorded in their durable bindings.

## Changed symbols

- `PhotonOriginalSessionResolver` is the frozen resolver contract. `createPhotonOriginalSessionResolver()` is its single implementation.
- For `turn.start` with a validated `NormalizedPhotonInput.replyTo`, the resolver reads the exact provider part from `PhotonMessageAuthorizationPort`, verifies the returned message remains in the same conversation and contains that exact message ID and part index, and returns its historical session and resource revision.
- For `approval.resolve`, the resolver reads the action binding before selecting the session. Authorization reads the current action again, compares it with the resolved historical session and revision, verifies actor, resource, expiry, current approval, and membership, then consumes the exact binding only during execution.
- Current conversation selection is consulted only when the operation has no historical reply or action reference.
- `messages` is optional only as a preparation-base transition. A historical reply without the durable reader fails closed with `reply_binding_missing`; it never falls back to current selection. Final coordinator composition must make the real reader required and remove the transition.
- `PhotonCoreClient.execute()` removes the caller-supplied checked proof, reconstructs the unchecked request, and authorizes it again immediately before the QM effect. Current membership, capability resource revision, run ownership, action binding, and revocation are therefore rechecked at execution.

## Audit corrections

The imported candidate introduced a different required message-reader port directly into the authorizer and did not implement the frozen resolver. The current audit added and used the exact resolver contract, kept the new reader transitional without forcing the preparation fixture to invent a no-op implementation, proved that an unwired historical lookup fails closed, and added separate execution-time checks for resource-revision revocation and run-ownership changes.

## Remaining limitations

Authorization is fresh at `PhotonCoreClient.execute()` and action consumption remains one-time, but this repair does not claim an atomic transaction across arbitrary QM effects. Production readiness depends on coordinator composition of the existing durable message store and restricted database grants. Missing or foreign historical bindings fail closed; the resolver does not infer a session from Photon, trust a caller session ID, or fall back to current selection.
