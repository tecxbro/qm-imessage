# R05 original-session authorization

## Reproducer

1. Link one Photon conversation to QM session A.
2. Bind a delivered provider message part and an approval action to A.
3. Change the conversation selection to session B.
4. Reply to the old A message or resolve the old A approval.

Before this repair, `authorize()` read the current conversation binding first and used B for the reply. The approval path compared its A-bound action to B and denied it. A new ordinary message correctly belongs to the current selection B, but historical replies and actions must retain the QM session recorded in their durable binding.

## Changed symbols

`src/api/photon-authorization.ts` previously resolved every operation from `PhotonConversationAuthorizationPort.find()` before looking at historical identities.

The repair adds `PhotonMessageAuthorizationPort.findByProviderPart()` and requires it as `PhotonAuthorizationDeps.messages`. For `turn.start` with `NormalizedPhotonInput.replyTo`, `authorize()` resolves the exact provider message part and verifies that the returned message still contains that exact message ID and part index in the same conversation. For `approval.resolve`, it resolves the action binding before comparing any claimed session. The current conversation selection is read only for operations without one of those historical references. All later QM visibility, resource revision, run ownership, approval, actor, expiration, and one-time consumption checks remain unchanged.

`src/api/photon-core-client.ts` did not require a change. Its `execute()` path removes the caller-supplied checked proof, reconstructs the unchecked request, and calls `PhotonAuthorizer.authorize()` again before dispatching to QM.

## API and composition delta

The R05-private adapter name is `PhotonMessageAuthorizationPort`. Its method shape is the read subset of the existing shared `MessageBindingStorePort.findByProviderPart()`, returning `providerMessage`, `qmSessionId`, `qmEntrySequence`, and `resourceRevision`.

The coordinator still needs to pass the existing durable message-binding store as `messages` when production composition constructs `createPhotonAuthorization()`. The coordinator-owned `test/photon-core-client.test.ts` fixture also needs a `messages.findByProviderPart()` implementation so the root typecheck can see the new required dependency. No fallback, provider query, latest-session choice, or fabricated part zero is permitted.

Requested coordinator-owned canonical documentation delta:

- `docs/imessage/contracts.md`, authority boundary: state that current conversation selection is the default only when no historical reply or action reference exists.
- `docs/imessage/architecture.md`, security: state that historical message and action bindings select the candidate QM session before current QM authorization is revalidated.
- `docs/imessage/lanes/wt-01.md`, boundary and factories: add the message-binding read dependency and original-session resolution behavior without changing Slack or web behavior.

## Verification

Node `v24.20.0` and npm `11.10.0` installed the locked dependency tree.

- `node --experimental-test-module-mocks --test test/photon-original-session-authorization.test.ts`: 5 passed, 0 failed.
- The same repair test against the unmodified preparation SHA: 2 passed, 3 failed. The failures reproduced the A reply being sent to B, unbound replies being accepted, and A-bound approvals being rejected after selection changed to B.
- `node --experimental-test-module-mocks --test test/photon-core-client.test.ts`: 8 passed, 0 failed.
- `tsc --noEmit`: blocked by the coordinator-owned `test/photon-core-client.test.ts` fixture omitting the new required `messages` dependency.

No PostgreSQL, live integration, activated route, Photon provider acceptance, or physical-device behavior was exercised by this repair.

## Remaining limitations

Authorization is fresh at `PhotonCoreClient.execute()` and action consumption is still one-time, but this repair does not claim an atomic transaction across arbitrary QM effects. Production readiness depends on coordinator composition of the existing durable message store and its restricted database grants. Missing or foreign historical bindings fail closed; the authorizer does not infer a session from Photon or fall back to the current selection.
