# R12 — Mount the existing Photon host through QM's authenticated web entry

## Scope

R12 registers the existing Photon presentation host at the QM web boundary. It does not add a Photon view adapter, a provider sender, a native iMessage extension, a replacement resource API, or a second authentication boundary. The repair starts at `4fc09eb065ddd459946e72dc4c88729491acb0f9` on `cp1/r12`, descended from the reviewed `integration-1` input `4b1ce5a8326979cb8cf59eb966df4906a901dd38`.

The coordinator-owned paths for this repair are `plugins/web-ui/server/index.ts`, `plugins/web-ui/src/main.ts`, `plugins/web-ui/src/shell.ts`, `plugins/web-ui/src/photon/registry.ts`, `plugins/web-ui/test/photon-registration.test.ts`, and this document. The supplied R12 text names `plugins/web-ui/test/repair-r12-host-entry.test.ts`, but the post-commit coordinator record at `docs/imessage/repairs/ownership.json` permits only `plugins/web-ui/test/photon-registration.test.ts`. This repair uses the recorded owned path and leaves the coordinator record unchanged.

## Reproducer

Before the repair, `plugins/web-ui/server/index.ts` dispatched the existing `/api/` routes without a Photon host entry. `plugins/web-ui/src/shell.ts` parsed the ordinary deep link, prefetched session/config state, mounted the ordinary shell, and opened its delivery stream for every path. `plugins/web-ui/src/main.ts` did not import the host stylesheet, and no registry module connected the existing host factory to the browser.

A valid `/photon` URL therefore had no dedicated authenticated host path. A malformed Photon query could fall through to ordinary web navigation, while a sign-out or model-auth transition had no host disposal or boot cancellation boundary.

## Repair symbols

The server now constructs `photonHostRoute` with `createPhotonHostRoute` and places it in the real `apiRoutes` array in `plugins/web-ui/server/index.ts`. The existing `routeRequest` `/api/` identity gate and `portalTokenStore` handler scope remain the only entry boundary. The current registration intentionally supplies an empty view set, a throwing unavailable contribution provider, and a denial authority because no production Photon contribution or canonical web authority adapter exists in this checkpoint. There is no success-shaped fixture.

The browser imports `./photon/host.css` from `plugins/web-ui/src/main.ts`. `plugins/web-ui/src/photon/registry.ts` exposes the empty `photonViewRegistrations` set and owns idempotent `disposePhotonEntry` and `mountPhotonEntry` calls around the existing `mountPhotonHost` factory. The server allowlist remains separately empty so adding a future browser adapter cannot expose it before the canonical server authority and contribution dependencies exist.

`plugins/web-ui/src/shell.ts` recognizes only the `UI_BASE`-relative `/photon` path, avoids ordinary prefetches before `/me`, completes the existing account and model-auth gates, parses the shared Photon query, mounts a dedicated root, and renders a visible unavailable state for malformed context. `bootEpoch`, `cancelBoot`, `renderAuthGate`, `signOut`, and `mountShell` dispose the Photon entry and prevent late `/me` work from remounting stale private content.

The shared names remain the existing `PhotonHostRequest`, `PhotonHostContext`, `PhotonViewRegistration`, `PhotonContributionProvider`, `createPhotonHostRoute`, `mountPhotonHost`, `loadPhotonHostContext`, `photonHostRequestFromQuery`, and `photonHostQuery`. No new provider or QM core API is invented.

## Why this is needed for iMessage

Photon app-card URLs and optional live rendering are presentation mechanisms. The pinned Photon sources do not provide QM authentication, installation or conversation authority, or a native QM view bridge. A Photon URL must enter through QM's current authenticated web surface, recheck current authority before exposing metadata, and use same-origin paths without putting a viewer or credential in the query. The host route is therefore additive presentation metadata, not a mutation capability or business authority.

## Acceptance cases

`plugins/web-ui/test/photon-registration.test.ts` exercises the actual exported server `handler` and the actual Vite-loaded browser `shell.boot` entrypoint:

- unauthenticated `/api/photon/host` is rejected by the existing identity gate before the unavailable route response;
- duplicate query context is rejected, unknown view syntax is invalid, and the explicit empty registry returns unavailable without private data;
- authenticated Photon boot waits for `/me`, does not prefetch ordinary sessions/config/split/inbox state, does not open the ordinary delivery stream, and uses a dedicated host root;
- malformed Photon context remains visible as an unavailable Photon entry instead of falling through to the ordinary shell;
- the existing model-auth gate completes before Photon mounting;
- sign-out during a delayed `/me` response invalidates the old boot, and a later reopen leaves one host root after replacement;
- `main.ts` imports the existing host-scoped stylesheet.

The existing `plugins/web-ui/test/photon-host.test.ts` remains a WT06 host-factory and lifecycle test. Its module-load hook and test-only authority/contribution are not used as proof of production registration.

## Remaining seams and evidence boundaries

The empty browser registry is intentional. No existing QM renderer currently exposes the standalone `PhotonViewRegistration` mount/cleanup contract, and no `PhotonContributionProvider` or `resolveAuthority` implementation exists in the web plugin. The current route consequently proves authenticated registration and fail-closed unavailable behavior only; it does not prove a successful business view, current membership revocation against a live database, provider acceptance, native iMessage embedding, device rendering, activation, or a human message round trip.

Wrong-installation, current-membership revocation, forwarded-context authorization, and unavailable-authority behavior cannot be exercised through a successful production host request while the registry and canonical dependency seams are absent. The WT06 test-only route covers the host factory's rejection behavior, but that is not production evidence. These acceptance items remain not run rather than passed.

`docs/imessage/repairs/contracts.md` assigns Photon route registration/classification to R09 and construction of concrete dependencies to R15. Those lanes must publish the canonical authority resolver and contribution provider before a nonempty production registry or success response can be added. `plugins/web-ui/src/conversations.ts` also keeps the ordinary delivery stream close function private; this repair avoids opening that stream on a fresh Photon entry but cannot dispose a stream from an ordinary shell that was already mounted in the same document. That coordinator-owned subscription seam remains required for in-document ordinary-to-Photon switching.

The read-only `createPhotonHostRoute` contract has no distinct missing-dependency response. With the legitimate empty view registry, an authenticated valid request returns its existing `404 {"error":"unavailable"}` response. Distinguishing missing host dependencies with `503 {"error":"host_unavailable"}` requires an exact coordinator-owned factory contract delta; this repair does not edit the read-only factory or add a parallel route.

Fresh-context review also identified two ordinary web races outside R12's owned paths: an already-started ordinary `refreshSessions` or session-open operation can mutate state after sign-out, and the async model-connect status loader can repaint after a later auth gate. R12 does not start those ordinary operations on a fresh Photon entry and does not expand into their owning modules. They remain separate QM issues.

The frozen source records remain unchanged. `docs/imessage/source-lock.json` records `content/app.md` at SHA-256 `81ae485a85373813cb78b50de592144527a5ddad80c0252e338e8aa01bdb4a11` and `messaging-features/apps.md` at SHA-256 `1ce74795d053c52245d10b3b375e3a2163ff8b30b18dac23fadf3719b82f6c40`. Those sources describe app-card URLs and optional installed-extension live rendering; they do not establish QM auth, provider delivery, or native-device evidence.
