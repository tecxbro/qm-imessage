## Verified acquisition contract

The frozen lock pins `spectrum-ts` and `@spectrum-ts/core` 12.8.0, `@spectrum-ts/imessage` 12.8.0, `@photon-ai/advanced-imessage` 2.1.0, and Photon CLI 2.2.0.

The shipped public `spectrum-ts` export `cloud.issueImessageTokens(projectId, projectSecret)` returns `Promise<TokenData>`. Its dedicated response is:

```ts
interface DedicatedTokenData {
  auth: Record<string, string>;
  expiresIn: number;
  numbers: Record<string, string | null>;
  type: "dedicated";
}
```

The frozen official explicit-client example uses `line-1.imsg.photon.codes:443`. The pinned `@spectrum-ts/imessage` implementation uses `auth[instanceId]` as the line bearer token, `numbers[instanceId]` as the line phone, `${instanceId}.imsg.photon.codes:443` as the server address, and `expiresIn` as the authoritative TTL. It reissues project credentials for automatic discovery and uses static tokens for explicit clients. R10 uses the same public issuer and provider-derived dedicated mapping without reproducing or inventing its HTTP endpoint.

The provider response supplies a TTL rather than an absolute expiry. R10 records the request start as a conservative acquisition time and converts the returned TTL to canonical ISO time. It reads the clock again after acquisition and rejects backwards, invalid, expired, or near-expiry results, so network time reduces the accepted remaining lifetime. The resolver rejects a credential at or inside the five-minute renewal margin.

The frozen and refreshed official connection page both distinguish project discovery from explicit clients and state that explicit client tokens require external renewal. The Advanced getting-started page requires a server address and bearer token but exposes no project-secret acquisition method.

## New symbols and behavior

`plugins/photon/src/provider/credentials.ts` adds:

- `ScopedLineCredential` and `LineCredentialResolution`
- `HostPrivateProjectSecretSource` and `IMessageTokenIssuer`
- `resolveLineCredential()`
- `createSpectrumCloudLineCredentialAcquirer()`
- `createSpectrumCloudLineCredentialResolver()`
- `PhotonLineCredentialResolver` and `createPhotonLineCredentialResolver()`

The host-private source must return a project secret with exact installation and project scope. The public Photon issuer receives that project secret and returns a dedicated token map. R10 selects only the exact line key, verifies its provider phone against the trusted `ProviderLine`, derives the same address as the pinned provider, converts the provider TTL to canonical expiry, and then validates exact provider, installation, project, line, phone, trusted address, and remaining-lifetime scope before returning `ready`. Generic acquisition requires an explicit trusted-address predicate; the Spectrum factory accepts only the exact pinned dedicated-line address mapping.

Every call reacquires credentials; no in-memory authority or stale-token cache exists. Line scope is snapshotted before asynchronous acquisition. Source errors, refresh errors, non-allowlisted error codes, unknown discriminants, prototype-inherited values, malformed fields, invalid clocks, wrong scope, absent lines, invalid expiry, shared token responses, and unsupported Advanced acquisition return safe unavailable codes. Thrown error text is discarded. A project secret is accepted only by the project-token issuer and is never copied into the returned line token.

`createPhotonLineCredentialResolver()` implements the prepared shared `available | unavailable | expired` projection with request-time installation, line, mode, and canonical-time validation. Available results carry the line bearer token, external renewal, persisted-line-assignment provenance, and canonical expiry. Address, phone, and project scope stay in the private ready result used by the connection coordinator.

## Coordinator deltas and limitations

The coordinator must supply a concrete `HostPrivateProjectSecretSource` from the approved private installation store, wire successful `ScopedLineCredential` values into R14's manager, and schedule external replacement before the renewal margin. Because the current manager consumes only address and token, R14 must revalidate the complete provider, installation, project, line, phone, trusted-address, and expiry tuple immediately before construction under its durable generation fence. Unavailable results must prevent construction and expose only their safe code. No public status or log may serialize the ready result.

The prepared shared contract's `PhotonLineCredentialResolution` is implemented as a projection, but it intentionally omits address, phone, and project scope. The manager requires address and token, while the Spectrum explicit client also requires phone. The coordinator must retain R10's private `ready { credential: ScopedLineCredential }` result inside the Photon process when wiring the connection and must not publish it.

Shared Spectrum credentials remain unavailable because `TokenData` exposes one token and TTL but no authoritative line ID or phone. Advanced mode remains unavailable because Advanced 2.1.0 exposes client constructors but no verified project-credential acquisition contract. Either path requires a coordinator-approved host-private exact-scope source before activation. R14 must fence concurrent renewal/replacement under durable line ownership; R10 does not manufacture an in-memory ownership substitute.

No live project secret, line token, or device was used. The implementation is compiled and fixture-tested, including existing connection callers. It is not yet coordinator-integrated, activated, provider-accepted, delivery-observed, or device-observed.
