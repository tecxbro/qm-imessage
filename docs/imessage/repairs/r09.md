## Reproducer

At the repair base, `createPhotonRoutes` returned eleven source-authenticated routes, but `src/api/routes/index.ts` neither imported the factory nor spread its routes into `apiRoutes`. The actual server iterates `apiRoutes`, so no Photon path reached its handler. Under signed portal-identity enforcement, a signed Photon POST was also treated as an unclassified write because `SYSTEM` contained no Photon paths.

The repair-specific regression imports the production `apiRoutes` and starts the exported `createServer`. It proves that all eleven Photon routes are present in the authenticated API table, absent from `rawRoutes`, dispatched through `ServerDeps.photonCore`, and processed by the ordinary source-auth and portal-identity classification middleware. The nine Photon writes are system routes, so source authentication reaches their handlers without a portal identity; unrelated portal-only routes remain portal-gated.

## Why iMessage needs this

The Photon process signs requests to QM's trusted channel boundary. Without production registration, its normalized iMessage operations, delivery acknowledgements, and context results cannot reach the existing authorization and QM application owners. Registering the existing factory activates that boundary while retaining separate source authentication and current human, conversation, run, approval, delivery, and context authorization inside the supplied core client.

## Shared API and composition handoff

R09 adds the already-agreed `ServerDeps.photonCore` seam and retains the canonical `createPhotonRoutes({ core })` signature with a required `PhotonCoreClient`. R15 remains responsible for constructing the concrete `createPhotonAuthorization()` and `createPhotonCoreClient()` from QM's existing application and durable stores, then supplying that client through `ServerDeps`. Until R15 does so, every correctly authenticated Photon route fails explicitly with `photon_not_configured`; there is no fixture core, fallback authorizer, second QM application, or production no-op.

The coordinator ownership record assigns the repair test path `test/photon-route-registration.test.ts`; that machine-verifiable path is used instead of the stale alternate filename in the prose assignment.

One coordinator integration blocker remains: the frozen contract requires the canonical route table to include Photon routes only when the typed dependency is available, but `src/api/server.ts` imports and iterates one static `apiRoutes` array before request context exists. That path is outside R09 ownership. The current static seam therefore registers source-authenticated Photon routes and returns the explicit `photon_not_configured` 503 when `ServerDeps.photonCore` is absent. Final integration must make server route-table construction dependency-aware, then use `createPhotonRoutes({ core: deps.photonCore })` only in the available branch and remove `serverPhotonRoutes`; the shared contract must not be weakened to bless the transitional registration.
