## Reproducer

At the repair base, `createPhotonRoutes` returned eleven source-authenticated routes, but `src/api/routes/index.ts` neither imported the factory nor spread its routes into `apiRoutes`. The actual server iterates `apiRoutes`, so no Photon path reached its handler. Under signed portal-identity enforcement, a signed Photon POST was also treated as an unclassified write because `SYSTEM` contained no Photon paths.

The repair-specific regression imports the production `apiRoutes` and starts the exported `createServer`. It proves that all eleven Photon routes are present in the authenticated API table, absent from `rawRoutes`, dispatched through `ServerDeps.photonCore`, and processed by the ordinary source-auth and portal-identity classification middleware. The nine Photon writes are system routes, so source authentication reaches their handlers without a portal identity; unrelated portal-only routes remain portal-gated.

## Why iMessage needs this

The Photon process signs requests to QM's trusted channel boundary. Without production registration, its normalized iMessage operations, delivery acknowledgements, and context results cannot reach the existing authorization and QM application owners. Registering the existing factory activates that boundary while retaining separate source authentication and current human, conversation, run, approval, delivery, and context authorization inside the supplied core client.

## Shared API and composition handoff
